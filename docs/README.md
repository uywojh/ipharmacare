# 技术方案：轻量、高性能、易维护

## 目标与原则

本项目先以患者和照护者使用的用药管理 MVP 为目标。技术选型优先考虑首屏快、运行资源少、部署简单和长期可维护；先采用模块化单体，不为尚未验证的规模提前引入微服务、消息队列或缓存集群。

医疗相关数据需要严格保护。性能优化不能以牺牲授权、审计、数据完整性或备份能力为代价。

## 推荐技术栈

| 模块 | 方案 | 选择理由 |
| --- | --- | --- |
| 前端 | TypeScript + 原生 HTML/CSS/DOM，使用 Vite 构建 | 当前页面以静态内容和少量交互为主。避免大型运行时框架，按需加载交互代码，静态资源可直接 CDN 缓存。 |
| 后端 | Go + 标准库 `net/http`，路由复杂时采用轻量 Chi | 单个小型服务即可承载 API 与健康检查；编译为单一可执行文件，内存占用和部署面相对小。 |
| 数据库 | PostgreSQL | 适合用药计划、服药记录、授权关系等结构化数据，并支持事务、约束和可靠备份。 |
| 数据访问 | `pgx` + 明确的 SQL 查询；查询增长后可引入 sqlc | 保持 SQL 可审查和类型安全，避免重 ORM 带来的隐式查询与额外复杂度。 |
| 部署 | 一个容器化 Go 服务 + 托管 PostgreSQL；静态资源优先由 CDN/对象存储提供 | 前后端可独立缓存和发布；无需常驻 Node 服务。MVP 可先由 Go 服务托管静态文件以减少运维部件。 |

## 架构草图

```text
浏览器（TypeScript 静态资源）
       │ HTTPS / JSON API
       ▼
Go 模块化单体（认证、用药、提醒计划、记录、照护者、报告）
       │ SQL / TLS
       ▼
PostgreSQL（事务、约束、备份）
```

首版不部署 Redis、Kafka 或独立微服务。若后续出现明确的任务量或可用性需求，再为异步提醒、缓存或分析任务引入独立组件。

## 性能策略

- 首屏只加载当前页面所需的脚本和样式；控制依赖数量，避免将整套 UI 框架送到浏览器。
- 图片使用合适尺寸和现代格式；字体尽量使用系统字体，减少第三方字体请求和隐私暴露。
- 静态文件启用压缩、长缓存和内容哈希；HTML 使用短缓存或重新验证。
- API 使用分页、明确字段投影和合理索引；避免 N+1 查询及无界历史记录读取。
- 用 PostgreSQL 事务确保用药计划变更和历史审计一致写入。
- 先通过真实使用数据和性能剖析定位瓶颈，再决定是否缓存或拆分服务。

## 安全与医疗数据要求

- 全站 HTTPS；会话使用安全、HttpOnly、SameSite Cookie，避免把长期凭证放在 localStorage。
- 服务端执行身份验证和资源级授权；照护者仅能访问患者明确授权的数据，并支持撤销。
- 对健康数据坚持最小化采集、最小权限访问、传输加密、备份加密和访问审计。
- 记录关键计划变更的操作者、时间和来源；服药反馈需区分患者记录、照护者代记及事后补录。
- 密钥通过部署平台密钥管理服务注入，不写入仓库；制定备份恢复和安全事件处理流程。
- 提醒与报告只基于已确认医嘱和用户反馈，不自动生成停药、补服、改量等个体化建议。
- 上线前结合实际服务地区评估医疗、隐私、数据留存和安全合规要求。

## 目录建议

```text
frontend/   TypeScript、样式、静态资源与前端构建配置
backend/    Go 服务、API、领域模块与数据库迁移
docs/       产品、架构、接口、安全和运维文档
tests/      单元、集成和端到端测试
```

## 实施顺序

1. 将现有静态页面拆分为可维护的前端文件，并保留小体积静态构建。
2. 明确用户身份、用药计划、服药记录、照护授权的数据模型与权限规则。
3. 建立 Go API、PostgreSQL 迁移、配置管理和健康检查。
4. 实现认证授权、用药计划、记录和可审计的变更历史。
5. 接入提醒与复诊摘要；通过专业审核确定所有医疗提示文案。
6. 补齐自动化检查、备份恢复演练、监控告警和发布回滚流程。

## 取舍与复核点

该方案适合目前的小型 MVP。若交互复杂度明显上升，可在实测基础上评估 Preact 等轻量组件层；若需要严格隔离静态前端与 API，可以统一部署到 CDN 与 API 域名并配置安全的跨域策略。任何技术调整都应由包体积、响应延迟、可靠性或开发效率的实际数据驱动。
